# AutoResilience v0.2 — Product Architecture Proposal

| | |
|---|---|
| **Type** | Decision (proposal, awaiting approval) |
| **Status** | Written for milestone P0. P1–P6 are implemented; §13 records the decisions taken since (D-4, D-5, D-9). |
| **Audited at** | `main` @ `e8407b0`, clean working tree, 2026-10-17 |
| **Scope** | Public website, self-hosted local tool (browser + future Tauri shell), future Cloud workspace |

The v0.1 engine (safety validation → baseline → pod-delete → observation → recovery → score)
and the console are the product core. v0.2 adds ways to deliver them. It does not change
how they work. Every section below says what it reuses.

## 1. Current architecture (as audited)

```
Browser ── Next.js console (apps/web, /api/backend/* rewrite) ── FastAPI (apps/api) ── PostgreSQL
                                                                   ├─ Reconciler thread (5 s tick)
                                                                   ├─ KubernetesAdapter   (read-only)      ┐
                                                                   ├─ PrometheusClient    (GET only)       ├─ kind "autoresilience"
                                                                   └─ LitmusChaosProvider (only writer:    ┘   shop, resilience-sandbox,
                                                                        own ar-<id> ChaosEngines)              monitoring, litmus
```

**Backend (`apps/api`).**
- FastAPI, SQLAlchemy 2 and Alembic. One `experiments` table, with evidence stored in JSON
  columns (`validation_result`, `baseline`, `chaos`, `observation`, `score`, `orchestration`).
  There are eight migrations.
- Routes: `/health`, `/ready`, `/experiments*` (create, list, get, validate, baseline, inject,
  observe, score, run, abort), `/experiments/history`, `/dashboard/summary` and `/services*`.
- Safety policies are defined in code and selected only by namespace
  (`domain/safety_policy.py`).
- Scoring is pure and versioned (v3 is current).
- The reconciler runs in-process and assumes a single API process.
- **There is no authentication, no CORS middleware and no tenancy.**
  `Settings.frontend_origin` exists but nothing uses it.
- `kube_context=None` falls back to the kubeconfig's *current* context (`kubernetes_adapter.py`,
  `chaos_provider.py`). This is safe on a developer laptop. It is unsafe for a packaged tool
  (§7.2).

**Frontend (`apps/web`).**
- Next.js 16.3.8, React 19.2.8, Tailwind v4 and TanStack Query 5. There are no UI or animation
  libraries.
- A single root layout (`src/app/layout.tsx`) hard-wires the console shell (Sidebar + TopBar)
  around every route. `/` is the operational Overview.
- Routes: `/`, `/experiments`, `/experiments/new`, `/experiments/[id]`, `/reports`,
  `/reports/[id]`, `/services`, `/services/[namespace]/[kind]/[name]` and `/settings`.
- Every page fetches data in the client from `/api/backend/*`. The rewrite target is baked in at
  build time.
- Design tokens live in `globals.css` (`@theme`: canvas/surface/line/fg/accent plus status
  colours, with print overrides). Primitives live in `src/components/ui`.
- Evidence is read only through `src/lib/evidence.ts`. Missing data is shown as "No data" and
  never guessed.
- API types are generated from `packages/contracts/openapi.json`, and CI fails on drift.

**Contracts (`packages/contracts`).** `openapi.json` is real. `coverage.*` and
`safety_policy.*` are placeholders. `package.json` declares `@autoresilience/contracts`, but no
npm workspace consumes it.

**Infrastructure.**
- `scripts/dev-cluster.sh` sets up a kind cluster with Prometheus chart 29.35.0 and litmus-core
  3.31.1, plus the sample `shop` app and the sandbox.
- `scripts/dev-db.sh` runs Docker Postgres. `scripts/gen-api-contracts.sh` regenerates the API
  contract.
- `infra/helm` and `infra/namespaces` are empty.
- The API and console run as host processes using the developer's kubeconfig.
- The load generator's `TARGETS` are fixed in the `shop.yaml` and `sandbox.yaml` env values.

**CI (`.github/workflows/ci.yml`).** Five jobs: backend (ruff, mypy, pytest), migrations on
Postgres, frontend (lint, typecheck, build), frontend tests (Vitest) and contract drift. No job
uses a cluster.

**Research evidence (`research/`).** The audit dated 2026-10-07
(`research/evidence-audit.md`, `research/handoff/14-current-evidence.md`) records **0 complete
AutoResilience experiment records (Level A)**. What survives:
- Six partial development runs, identified from surviving ChaosEngines (Level B1).
- Unattributed telemetry (B1).
- Runs documented only in docs (B2).

This matters for the playground (§8).

### Limitations relevant to v0.2

| Limitation | Consequence |
|---|---|
| Unauthenticated API with full write access to experiments | Must never be reachable outside loopback. Rules out exposing the current backend for the website or Cloud. |
| One root layout owns every route; `/` is the console | A marketing site cannot share the app without restructuring the routes. |
| Console needs a live API through a build-time rewrite | It cannot be a static site. A packaged build must fix the API URL at build time. |
| Dynamic `[id]` routes with client fetching | `output: "export"` is not possible without changing the routes. Relevant for Tauri. |
| Developer kubeconfig, current-context fallback | A packaged tool could silently target the wrong cluster. |
| Load-generator targets are hard-coded | Imported applications get no client evidence until this is generalised. |
| No complete experiment records exist | The playground has nothing genuine to replay until a controlled campaign runs. |

## 2. Target architecture

```
                     ┌───────────── shared, unchanged core ─────────────┐
                     │  FastAPI engine: safety · baseline · Litmus ·      │
                     │  recovery · scoring v1–v3 · history/reports        │
                     └──────────────▲───────────────────▲─────────────────┘
                                    │ loopback only      │ (future) per-tenant, behind gateway
  ┌──────────────────────┐   ┌──────┴────────────┐   ┌───┴──────────────────────────┐
  │ Public website       │   │ Self-hosted local │   │ Cloud workspace (future)     │
  │ apps/site            │   │ apps/web console  │   │ apps/web console + auth      │
  │ static export, CDN   │   │ + local stack     │   │ gateway + tenancy + connector│
  │ NO backend access    │   │ + service manager │   │ outbound-only cluster agent  │
  │ replays recordings   │   │ + Tauri (later)   │   │                              │
  └──────────▲───────────┘   └───────────────────┘   └──────────────────────────────┘
             │ build-time import of sanitized, schema-validated JSON
  ┌──────────┴────────────────────────────────────┐
  │ Recorded evidence: apps/api exporter (read-only) → sanitizer → schema → content/recordings │
  └───────────────────────────────────────────────┘
```

**Principles.**
1. **One engine.** Every delivery experience calls the existing FastAPI services. Nothing
   re-implements safety, recovery or scoring (this is already a frontend rule in
   `DEVELOPMENT.md`).
2. **The public website never talks to an engine.** It ships static files and recorded JSON
   only.
3. **The engine never gets new cluster-write powers.** Provisioning and import writes belong
   to a separate, local-only service manager with its own allowlist. The API keeps its two
   writers: the database and its own ChaosEngines.
4. **Grow the repository structure only when a second consumer exists.** No monorepo tooling
   (Turborepo or Nx). npm workspaces are added only when `apps/site` first imports shared code
   (§4).

## 3. Public website: same app or separate app?

**Recommendation: a separate Next.js app, `apps/site`, built with `output: "export"` (fully
static).**

| Concern | Same app (route groups) | Separate `apps/site` (recommended) |
|---|---|---|
| Exposure of the unauthenticated API | A public deployment carries the `/api/backend/*` rewrite and console routes. One wrong env var exposes the engine. | No rewrite and no API client in the bundle. Exposure is structurally impossible. |
| Hosting | Needs a Node server (rewrites are not supported by static export) | Any static host or CDN. Reproducible, cacheable, cheap. |
| Bundle weight | three.js and scroll-animation code risk leaking into console chunks. Two styles of performance budget in one build. | 3D and MDX dependencies stay out of the console, which stays small for Tauri. |
| `/` conflict | `/` is the console Overview and must move (for example to `/app`), which breaks existing links and tests. | Console URLs stay unchanged. |
| Release cadence | Copy edits redeploy the console | Independent |
| Reuse of the experiment room for replay | Direct | Needs shared code: tokens, primitives, evidence readers and replay-safe room components |
| Tauri | The desktop build must strip marketing routes | Console only |

**Tradeoff accepted:** shared code must be extracted. This is limited to:
- the `@theme` tokens;
- `components/ui/*`;
- `lib/evidence.ts`, `lib/experiment-state.ts` and `lib/format.ts`;
- the presentational parts of the experiment room (lifecycle, impact/recovery, score panel).

The room components (`lifecycle`, `impact-recovery`, `score-panel`) already take an `Experiment` as props and do not fetch. A recording only needs to supply that shape.

## 4. Routing, application structure and shared code

### 4.1 Repository layout (additions only)

```
apps/
  api/                          unchanged engine; + app/tools/export_recording.py (P1)
  web/                          console (unchanged URLs); later + /onboarding, /help
  site/                         NEW (P2): static marketing, docs, downloads, playground
  desktop/                      NEW (P8): Tauri shell (Rust + config only, no UI code)
packages/
  contracts/                    + recorded-experiment.schema.json (P1, generated from Pydantic)
  ui/                           NEW (P2, when apps/site needs it): tokens.css, primitives,
                                evidence readers, replay-safe room components (source-only TS)
tools/
  ar/                           NEW (P5): local service manager CLI (later embedded by Tauri)
```

### 4.2 Shared-code strategy

- **Stage 0 (now): nothing moves.**
- **Stage 1 (P2): extract `packages/ui`.**
  - Add `"workspaces": ["apps/web", "apps/site", "packages/*"]` in a root `package.json`.
  - Consumers use `transpilePackages: ["@autoresilience/ui"]`. Source-only TypeScript, so no
    build step.
  - `apps/web` imports switch from `@/components/ui/*` to `@autoresilience/ui/*` in one
    mechanical commit, and the existing Vitest suite verifies it.
  - The CI `npm ci` steps move to the root.
- **Contracts.** `openapi.json` and the generated `schema.ts` remain the API contract. The new
  recording schema lives beside them. Both are generated from Pydantic, never written by hand.
- **Rule.** Shared components take evidence as props and never fetch. Fetching stays in
  `apps/web/src/lib/api`. This is what lets the playground render the same components from a
  recording.

### 4.3 Routes

**Public website (`apps/site`, static).**

| Route | Purpose |

**Product workspace (`apps/web`; existing URLs kept).**

## 5. Desktop integration strategy

**Recommendation: a thin Tauri v2 shell over a local stack. It does not bundle Python or Node.**

Docker is already a hard requirement because kind runs on it. So the local tool runs the
engine as containers, and the desktop shell only supervises them.

```
Tauri shell (apps/desktop, Rust)
  ├─ window → http://127.0.0.1:<port>   (console served by the local stack; same-origin, no CORS)
  └─ Rust commands (allowlisted, no shell passthrough) → service manager (tools/ar)
          ├─ docker compose -p autoresilience  (api, postgres, web)   ← images pinned by digest
          ├─ kind create/delete cluster --name autoresilience           ← only this name
          └─ helm/kubectl against context kind-autoresilience only
```

- **Why not static export inside Tauri?**
  - The console's `[id]` routes and the build-time rewrite would both need changes.
  - The API still needs a backend process anyway.
  - Serving the console from the local stack keeps one console build for browser and desktop.
- **Why not sidecar binaries (PyInstaller and Node)?** Larger installers, per-OS packaging of
  `psycopg` and `kubernetes`, and two runtimes to patch. Containers reuse what the user already
  has.
- **Tauri capability config:**
  - no `shell:allow-execute` for arbitrary commands;
  - only named commands (`stack_up`, `stack_down`, `cluster_create`, `cluster_delete`,
    `status`, `open_logs`);
  - every argument validated in Rust;
  - the webview loads only `127.0.0.1`.
- **Order.** The browser-based local stack (P5) ships first. Tauri (P8) is a convenience layer
  on top of the same `tools/ar` logic, so there is no desktop-only behaviour.

## 6. Local installation model

| Concern | Design |
|---|---|
| Distribution | `ar` CLI (single binary or `pipx`) plus `compose.yaml`. Images published with SBOM and signature, pinned by digest. |
| Processes | `ar up` starts `postgres` (named volume `autoresilience-data`), `api` (`ORCHESTRATOR_ENABLED=true`) and `web` (Next.js `output: "standalone"`, `AUTORESILIENCE_API_URL=http://api:8000` at image build time). |
| Network | Ports published on `127.0.0.1` only. The API is reachable only from the `web` container and loopback. The containers join the `kind` Docker network to reach the cluster. |
| Cluster access | The API container gets a **generated kubeconfig** for a dedicated ServiceAccount (`kind get kubeconfig --internal` for bootstrap only, then RBAC-scoped; this resolves E-03 in `research/handoff/21-future-work.md`). `KUBE_CONTEXT` is always set explicitly, and the API refuses to start if it is unset in packaged mode. |
| Prometheus | Inside the cluster, at `http://<kind-node>:30090` on the kind network (the existing NodePort). |
| Local state | `~/.autoresilience/state.json`: created cluster name, granted permissions, imported apps, image digests. This is the source of truth for cleanup. |
| Upgrades | `ar upgrade` pulls new digests, backs up with `pg_dump` to `~/.autoresilience/backups/`, then runs `alembic upgrade head` (the existing migrations). |
| Uninstall | `ar down` stops containers and keeps data. `ar uninstall` asks separately whether to delete the cluster *it created* and whether to delete data, offering a backup first. |

A future `infra/helm` chart (engine inside the cluster) is the basis of the Cloud connector. It
is not needed for local use.

## 7. Kubernetes and Docker onboarding (design only; no import in v0.2 P0)

### 7.1 Onboarding flow

```
1 Environment ─▶ 2 Permissions ─▶ 3 Cluster ─▶ 4 Application ─▶ 5 Config review ─▶ 6 Health & traffic ─▶ 7 First experiment
  detect           explicit,        create or      K8s manifests      secret/hazard      endpoint, loadgen      existing builder
  Docker/kind      per capability   verify kind    OR Compose file    report, consent    target, baseline       (/experiments/new)
```

1. **Detect the environment** (read-only).
   - Docker: `docker version` / `docker info` (or Podman's Docker-compatible socket).
   - Memory and CPU available to the runtime. Minimum thresholds are to be measured in P5. The current stack
     with Prometheus and Litmus has not been profiled.
   - `kind`, `kubectl` and `helm` versions against pinned minimums. Missing tools are
     offered as a download with checksums, never installed silently.
   - Each finding is reported as `OK | MISSING | INSUFFICIENT | ERROR`, using the same status
     vocabulary as the safety checks.
2. **Explicit permissions.** One consent per capability, stored in `state.json` and
   revocable in `/settings/permissions`:
   - *use the Docker daemon*;
   - *create cluster `autoresilience`*;
   - *pull listed images*;
   - *read and build the selected Compose project directory*;
   - *apply manifests into AutoResilience-owned namespaces*.

   Nothing is done before consent. Declining leaves the tool usable for viewing history.
3. **Provision the cluster.** The existing `infra/kind/cluster.yaml` and the
   `dev-cluster.sh` steps, ported into `tools/ar`.
   - Idempotent.
   - Only the name `autoresilience`.
   - If a cluster with that name exists but `state.json` did not create it, the tool stops
     and asks. It never adopts or deletes another cluster.
4. **Connect an application.** Two separate paths.
   - **Kubernetes path (default for v0.2).** The user provides YAML, a Helm chart or a
     kustomize directory, which is rendered locally.
     - Supported kinds: Deployment, StatefulSet, Service, ConfigMap, Secret (local only),
       ServiceAccount.
     - Applied into a new namespace `app-<slug>`, labelled
       `app.kubernetes.io/managed-by=autoresilience`.
     - Rejected: cluster-scoped objects, CRDs, RBAC bindings, `hostPath`, `hostNetwork`,
       `privileged`, added capabilities, NodePort/LoadBalancer.
     - **Existing external clusters** (attach to a user's cluster instead of copying into
       kind) are a separate, later path. It needs an explicitly chosen context, a scoped
       ServiceAccount, a namespace allowlist and a policy review. It is not in v0.2.
   - **Docker path.**
     - *Image*: a single image with port and health path.
     - *Compose*: parse a supported subset (`image`, `build`, `ports`, `environment`,
       `env_file`, `healthcheck`, `depends_on`, `deploy.replicas`). This is converted into a
       Deployment and Service per service.
     - `build` uses local `docker build`, then `kind load docker-image`. No registry upload.
     - Unsupported keys (`privileged`, `network_mode: host`, `devices`, `cap_add`, bind
       mounts, `pid`) are a hard error with an explanation, never silently dropped.
5. **Configuration and secret review** (runs locally and does not leave the machine).
   - Flags environment variables whose names match `PASSWORD|SECRET|TOKEN|KEY|CREDENTIAL|DSN`.
   - Flags high-entropy values, `env_file`, Compose `secrets` and files under the build context
     that match common credential files (`.env`, `*.pem`, `id_*`, `kubeconfig`).
   - The user chooses per item: create a Kubernetes Secret in the local cluster, replace it with
     a placeholder, or abort.
   - Values are never logged, never written to the AutoResilience database, never included in
     experiment evidence, and never exported.
   - The report stores only key names and the chosen action.
6. **Health checks and test traffic.**
   - The user selects an HTTP endpoint (default: the Compose `healthcheck` or the readiness
     probe path).
   - The tool adds the target to the load generator by turning `TARGETS` into a
     per-application ConfigMap entry that the tool owns. Requests are GET-only,
     rate-capped (the existing loadgen sends one sequential request per `INTERVAL_SECONDS`, 0.1 s in `shop.yaml`, about 10 req/s per target) and stay inside the cluster.
   - The existing **baseline** step decides whether the app is ready to test. A missing client
     metric stays `UNAVAILABLE`, which is existing behaviour.
7. **First experiment.** The flow hands off to `/experiments/new?namespace=&kind=&name=`
   (existing). The safety policy is resolved by namespace as today. Imported namespaces get the
   `default` policy unless a code-reviewed mapping says otherwise. **No policy choice is
   exposed through onboarding.**

### 7.2 Hard rules for the service manager

- It acts only on context `kind-autoresilience`, verified by cluster name and the
  `state.json` record before every write.
- Every object it creates carries `app.kubernetes.io/managed-by=autoresilience` and
  `autoresilience.io/owner=local-manager`. Cleanup deletes only objects carrying both labels,
  in namespaces it created, following the label-verified pattern of `delete_owned`.
- The engine API gains **no** apply or import endpoints. The console reaches the service
  manager through a separate loopback endpoint (P5 decision §12, D-4) or through Tauri
  commands.
- Litmus input stays typed fields only. There is no arbitrary YAML, no custom experiments and
  no plugins, as today (`chaos/policies/safety-policy.md`).

## 8. Public playground: recorded evidence replay

### 8.1 Pipeline

```
PostgreSQL (Level A records only)
   │ read-only transaction (SET TRANSACTION READ ONLY), by explicit experiment id
   ▼
apps/api/app/tools/export_recording.py   ── Pydantic model RecordedExperiment (allowlist)
   │ sanitize → canonicalize (sorted keys, UTC) → sha256
   ▼
recordings/<id>.json  ── validated in CI against packages/contracts/recorded-experiment.schema.json
   │ manual review + commit (signed-off)                      (generated from the same Pydantic model)
   ▼
apps/site/content/recordings/  →  static build  →  /playground/[recordingId]
```

- **Export.** A CLI only, not an HTTP endpoint. It reuses the existing ORM model and the
  `ExperimentRead` schema. It refuses experiments that are not in a terminal state, and it
  refuses experiments whose `score.version` it does not know.
- **Sanitize** by allowlist, not denylist.
  - **Kept:**
    - state and timestamps;
    - target kind;
    - fault, mode, duration and replicas;
    - validation check names and statuses;
    - the policy snapshot;
    - baseline metric values;
    - Litmus verdict and phase;
    - recovery finding;
    - impact and outage numbers;
    - orchestration events;
    - the score with its version and breakdown.
  - **Pseudonymised:** namespace and workload names outside the shipped sample apps
    (`shop`, `resilience-sandbox`), and pod names, using stable per-recording aliases.
  - **Dropped:**
    - Kubernetes UIDs, `managedFields` and raw Litmus objects;
    - hostnames and IPs;
    - kube context;
    - free-text `description`;
    - anything not in the allowlist.
- **Version.** `schema: "autoresilience-recording/1"`. A breaking change means `/2`. Older
  files remain valid against their own version. This is the same rule as score versioning.
- **Provenance block** (required):
  - `evidence_level: "A"`;
  - `captured_at`, `exported_at`;
  - `engine_commit`, `exporter_version`;
  - `score_version`;
  - `environment` (for example `kind, single node, sample apps`);
  - `content_sha256`.

  The JSON-Schema `const` on `evidence_level` makes partial or synthetic data unpublishable.
- **Validate.** A CI job validates every committed recording with Pydantic, so no new
  dependency is needed, and it checks that the hash matches. Test fixtures live under
  `apps/api/tests/` and are marked `synthetic: true`. The site build refuses such files.
- **Replay.**
  - Pure client-side, with no network calls.
  - A timeline scrubber is driven by recorded `orchestration` events and `state_since`
    timestamps.
  - The same shared room components (§4.2) render from props.
  - The topology view highlights the deleted pod and its replacement at recorded times.
  - Gaps are shown as gaps, never interpolated (the `evidence.ts` rule).
  - There are no "run", "retry" or "edit" affordances.
- **Labelling.**
  - A persistent banner: "Recorded evidence: real run captured <date> on <environment>.
    Nothing is executed."
  - The provenance drawer shows the full provenance block and hash.
  - Score explanations link to the matching methodology version.

### 8.2 Precondition

The latest audit found **zero Level A records**. The playground and any data-driven hero
cannot ship real content until a controlled campaign (E1–E4 in
`research/handoff/16-final-experiment-matrix.md`) is run into the persistent database and
exported.
- B-level partial records (`research/experiment-results.json`) are **not** replayable. They lack
  complete evidence.
- Until real recordings exist, the site shows an honest empty state ("recordings will appear
  after the evaluation campaign") rather than placeholder data.

## 9. Security and trust boundaries

```
┌─ Public internet ─────────────┐   ┌─ User machine (trusted by the user) ──────────────────────────┐
│ apps/site static files        │   │ Browser / Tauri ──▶ 127.0.0.1: web ──▶ api ──▶ postgres         │
│ recordings (sanitized, public)│   │                          ▲ (loopback / compose network only)    │
│ release artefacts (signed)    │   │ service manager ─▶ docker, kind "autoresilience" (owned only)    │
└───────────────────────────────┘   │ api ─▶ cluster via scoped ServiceAccount (read + own ChaosEngines)│
          ▲  no path back            └────────────────────────────────────────────────────────────────┘
          └── nothing flows from user machines to the site, except recordings a maintainer commits
┌─ Cloud (future) ──────────────────────────────────────────────────────────────────────────────────┐
│ authN/Z gateway ─▶ tenant-scoped engine ─▶ tenant DB      ◀── outbound-only mTLS ── customer agent │
│ (existing API is never exposed directly; agent holds cluster creds, never uploads secrets)        │
└───────────────────────────────────────────────────────────────────────────────────────────────────┘
```

| Boundary | Rule |
|---|---|
| Engine API | Loopback or private network only, until an auth layer exists. Packaged mode binds `127.0.0.1` and refuses `0.0.0.0` unless `AUTH_MODE` is configured (future). |
| Cluster writes | Engine: only `ar-<id>` ChaosEngines (unchanged). Service manager: only labelled objects in owned namespaces in the owned cluster. |
| Kube context | Always explicit. Never the current-context fallback in packaged mode. |
| Secrets | Detected and handled locally (§7.1 step 5). Never stored in experiment evidence or exported. Never sent anywhere. |
| Telemetry | None by default. Any future usage telemetry is opt-in, documented field by field, with no identifiers, names or evidence. |
| Updates and downloads | Signed artefacts with published checksums. Images pinned by digest. The CLI verifies them before running. |
| Public recordings | Allowlisted fields, maintainer review, hash-pinned. The site has no backend. |
| Cloud | Separate auth gateway and tenancy. Customer connector is outbound-only, scoped RBAC, and runs the existing read-only adapter and own-CR writer in-cluster. Source code, kubeconfigs and Secrets never leave the customer environment. |
| Fault surface | `pod-delete` only (current `SUPPORTED_FAULT_TYPES`). New faults arrive only as vetted, code-reviewed builders. No user YAML, executables or plugins. |

## 10. Free vs paid feature boundaries

| Community Edition (free, self-hosted, complete) | Paid (Cloud / Team / Enterprise) |
|---|---|
| All fault types the engine supports, safety validation, policies | Managed hosted workspace (no local stack) |
| Baseline, injection, observation, recovery, all score versions | Multi-user collaboration: shared projects, comments, review/approval of runs |
| Experiment history, services, printable reports, export | Fleet management: many clusters and connectors, cross-cluster views |
| Local onboarding (K8s and Docker paths), local cluster | Long-term retention, scheduled runs, trend analytics across teams |
| API and CLI | SSO/SAML, RBAC, audit-log export, policy approval workflows |
| Recording export | Support, SLAs, compliance packaging |

**Rule:** a paid feature may *manage, share or retain* results. It may never *gate* a core
test, a safety check, an evidence field or a score component. The engine has no edition
checks. Editions are implemented only in the Cloud layer.

## 11. Frontend design

### 11.1 Visual direction

- **Palette.** Keep the existing console tokens (`canvas #0a0e19`, surfaces, `accent #4f8bff`,
  status colours reserved for meaning). The site uses the same tokens with more negative space
  and larger type. There are no new brand gradients. One restrained accent glow is allowed for
  the active path in the hero.
- **Hero.** A 3D service topology of what AutoResilience actually tests:
  - nodes are workloads: `frontend ×3 → checkout ×2 → cart-redis`, with `loadgen` as the
    client;
  - edges are request paths;
  - a slow camera pan shows a pod-delete: the pod dims, request edges flicker for errors, a
    replacement pod spins up, and the edges return to steady state;
  - the score resolves at the end.

  Once a real recording exists, the hero's timing comes from it. Until then the hero is
  labelled "illustration". No decorative globes, particles or abstract meshes.
- **Navigation.** A floating, translucent top bar (blurred surface, 1px `line` border, slight
  shadow). It condenses on scroll. Docs get a sticky sidebar plus "On this page".
- **Scroll.** Each major section shows one lifecycle phase: validate → baseline → inject →
  observe → recover → score. Motion is a short ease (≤ 400 ms). Pinned sections are used only
  where they explain sequence. No parallax for its own sake.
- **Console.**
  - Information-dense: compact tables, mono numerics, and the existing badges and stepper.
  - Live pipeline view: a horizontal phase rail with per-phase elapsed time, current evidence
    and deadline countdowns (data already in `orchestration`).
  - Motion only for state change.
- **Accessibility.**
  - Every interactive element is reachable by keyboard and uses the existing
    `:focus-visible` outline.
  - The 3D canvas has `aria-hidden` and an equivalent text/SVG description.
  - `prefers-reduced-motion`: the static SVG topology is rendered instead of WebGL, and
    scroll-linked animation is disabled.
  - The replay scrubber is a native range input with keyboard steps per event.
  - Contrast stays at WCAG AA or better for text and non-text UI.
- **Fallbacks.** No WebGL, or a low-power device, gets the same static SVG. The hero loads
  after the LCP text. The 3D bundle is lazy-loaded and capped at about 200 KB gzip.

### 11.2 Information architecture

- **Public website:** see §4.3.
- **Workspace.** The sidebar keeps Overview, Experiments, Services and Reports. It gains
  **Applications** (P6) and keeps Settings. **Help** and the API status move to the footer.
- **First-run onboarding.** Shown when `/ready` is OK but there are no experiments and no
  applications. Seven steps (§7.1), each resumable. Each step shows its exact actions and the
  permissions requested before running. Each step can be skipped by connecting the sample
  `shop` app.
- **Experiment builder.** Existing Configure → Safety → Review. Additions:
  - a target picker grouped by application;
  - a summary of policy and blast radius before submission;
  - an explanation of "why this check failed" that links to the policy docs.

  No client-side safety rules.
- **Live pipeline.** The existing experiment room plus the phase rail:
  - **Overview** tab: fault → impact → recovery;
  - **Metrics**;
  - **Events**: `orchestration.events`;
  - **Evidence**: raw JSON with copy.

  Abort is always visible while the run is active.
- **Results and reports.** The existing report view plus:
  - a "score methodology vX" link;
  - an evidence completeness indicator (which components were `NOT_APPLICABLE` or
    `UNAVAILABLE`);
  - export recording (P1 CLI; console button later).
- **Settings:** connection, cluster (context, owned resources), permissions (granted consents,
  revoke), data (backup, retention, cleanup preview listing exactly what will be deleted).
- **Help:** bundled docs, diagnostics bundle (versions, `/ready`, environment checks;
  secret-free by construction) and keyboard shortcuts.

## 13. Risks and decisions requiring approval

### Risks

| Risk | Mitigation |
|---|---|
| No genuine recordings exist, so the website's central feature has no content | Run the controlled campaign before P3. Ship an honest empty state, never sample data. |
| Accidental public exposure of the unauthenticated API | Separate static site; loopback binding and refusal in packaged mode; no auth-less Cloud |
| Packaged tool targets the wrong cluster through the current context | Explicit context, owned-cluster verification before every write |
| Import path becomes a general "apply anything" tool | Strict kind/field allowlist, owned namespaces, hard errors on hazards, no engine endpoints |
| Secrets leak into evidence or recordings | Local-only scanner, allowlist export, no free-text fields exported |
| Local resource demands (kind + Prometheus + Litmus, not yet profiled) exceed laptops | Measure in P5; preflight resource check with clear thresholds; document requirements on `/download` |
| Shared-code extraction destabilises the console | One mechanical commit, existing Vitest suite plus typecheck as the gate |
| Single-process reconciler assumption breaks under Cloud scale | Cloud milestone adopts DB row locks (already listed in future work) |
| 3D hero hurts performance or accessibility | Lazy-load, size budget, SVG fallback, reduced-motion default respected |
